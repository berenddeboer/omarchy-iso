# Omarchy ISO With ZFS Support

Use this skill when rebuilding, debugging, or validating an Omarchy ISO that adds the experimental ZFS root install path with encrypted per-user ZFS homes to the normal Omarchy ISO.

This is not the upstream/default Omarchy ISO path. It depends on both this ISO repository and a local Omarchy source checkout that contains the ZFS-aware Limine/mkinitcpio changes.

## Required Local Sources

Work from the ISO repository:

```bash
cd ~/src/omarchy-iso
```

Build from the local Omarchy checkout:

```bash
OMARCHY_PATH="$HOME/src/omarchy" ./bin/omarchy-iso-make --local-source --no-cache --no-boot-offer
```

The local Omarchy checkout must include the ZFS-aware `install/login/limine-snapper.sh` behavior:

```text
install/login/limine-snapper.sh
```

For ZFS roots, that Omarchy script must install `limine-mkinitcpio-hook`, write mkinitcpio hooks with `zfs filesystems`, omit `fsck`, and include `/etc/hostid` in the generated initramfs/UKI. The initial Limine cmdline generated by the ISO must include `zfs_boot_only=1`; Omarchy then preserves it when it regenerates `/boot/limine.conf`.

## What The ISO Patch Does

The configurator adds a root filesystem selector:

```text
configs/airootfs/root/configurator
```

It writes `root_filesystem.txt` and supporting installer state files. Btrfs keeps the existing encrypted Archinstall flow. ZFS uses a manual install path.

## Known Installer Debt

The current ZFS path is a second installer, not just a ZFS variant of the Btrfs installer. This is intentional only as a temporary experimental path and must be addressed. The goal is to use Archinstall for ZFS just as the Btrfs path does: prepare the ZFS pool/datasets and mount tree first, run Archinstall with `pre_mounted_config` to install and configure the base OS, then apply only the ZFS-specific post-install work.

Problems caused by bypassing Archinstall today:

- The generated ZFS config includes `network_config: { "type": "iso" }`, but the manual ZFS path never runs Archinstall, so the ISO network handoff is skipped.
- The ZFS target enables `systemd-networkd` and `systemd-resolved` but does not copy/write the ISO `.network` files or configure `/etc/iwd/main.conf`. Real Wi-Fi installs can associate through iwd without getting DHCP/IP addresses. QEMU VM tests do not prove this works because they use wired virtio networking.
- Boot and EFI setup can drift from the Btrfs path. The ZFS path manually copies Limine files and writes entries instead of relying on the same Archinstall/Omarchy handoff used by Btrfs.
- The base package set can drift. The ZFS `pacstrap` list is hand-picked and can miss packages included in the Archinstall/offline baseline, such as network, firmware, boot, or service dependencies.
- Time sync, user creation, locale, hostname, hosts, sudoers, fstab, initramfs, and service defaults are manually reproduced and therefore easy to miss or subtly diverge from Archinstall behavior.
- Snapshot and rollback behavior is not aligned with the Btrfs Snapper path. ZFS dataset creation exists, but a comparable policy still needs deliberate design.
- Automated ZFS VM validation currently checks boot, ZFS datasets, PAM, Limine, SDDM, and failed units, but it does not verify that the installed system obtains an IP address.

When replacing the manual ZFS base install with Archinstall, verify `pre_mounted_config` behavior before removing safeguards. In particular, confirm what Archinstall does with `fstab`, bootloader files, NVRAM entries, initramfs generation, users, networking, and any crypttab-like output, then decide which steps are delegated to Archinstall and which remain ZFS-specific post-install steps.

The automated installer dispatches based on the selected filesystem:

```text
configs/airootfs/root/.automated_script.sh
```

For ZFS it creates an unencrypted pool named `zroot`, uses `zroot/ROOT/default` for `/`, creates `zroot/data/home` for `/home`, and creates an encrypted per-user dataset at `zroot/data/home/$OMARCHY_USER`. It also creates child datasets for `/var/log`, `/var/cache`, `/var/tmp`, and selected `/var/lib/*` paths.

The per-user home dataset uses the installer encryption password as its initial ZFS passphrase:

```text
encryption=on
keyformat=passphrase
keylocation=prompt
mountpoint=/home/$OMARCHY_USER
```

ZFS passphrases must be at least 8 characters, so the configurator enforces an 8-character minimum password. The installer creates the user with `useradd -M -d /home/$OMARCHY_USER` so user creation does not hide or replace the encrypted dataset mount.

The root dataset must be mounted before creating child datasets. Creating children before mounting `zroot/ROOT/default` hides `/home` and `/var/log` under the root dataset after root is mounted.

The ZFS installer path writes initial Limine entries like this:

```text
root=ZFS=zroot/ROOT/default rw zfs_boot_only=1 console=ttyS0,115200n8 console=tty1
```

`zfs_boot_only=1` prevents the OpenZFS initramfs late hook from running a broad late `zpool import -a`. Without it, otherwise successful boots can briefly show:

```text
no pools available to import
```

The installer enables ZFS userspace services in the target:

```text
zfs-import-cache.service
zfs-import.target
zfs-mount.service
zfs.target
```

It also keeps hard assertions around the target mounts and chroot HOME path so `/home` must resolve to `zroot/data/home` and `/home/$OMARCHY_USER` must resolve to `zroot/data/home/$OMARCHY_USER` throughout the Omarchy install.

## Login And Home Unlocking

The ISO uses `pam_zfs_key.so` from `zfs-utils` plus an auth-time `pam_exec.so expose_authtok seteuid` helper to unlock the encrypted user home during password login. The helper mounts the home during `auth`, after `pam_unix` has accepted the password, so graphical display managers cannot continue into the unmounted parent `/home/$OMARCHY_USER` if PAM session token caching fails. The installer writes `/etc/pam.d/zfs-key`, includes it from `system-login` and `su-l` for auth/session login, and keeps only the password-change hook in `system-auth`:

```text
pam_exec.so expose_authtok seteuid quiet /usr/local/lib/omarchy/zfs-pam-unlock-home
pam_zfs_key.so homes=zroot/data/home runstatedir=/run/pam_zfs_key
```

For screen unlocks, hyprlock keeps the packaged `/etc/pam.d/hyprlock` file that includes `login`. The ZFS stack is scoped to login services (`sddm`, `login`, `sshd`, and `su-l`), so the `hyprlock` PAM service skips the privileged ZFS home unlock logic while still using the distro PAM chain for password verification.

SDDM autologin must be removed for ZFS encrypted-home installs because the home passphrase needs a real password login. The installer removes `/etc/sddm.conf.d/autologin.conf`, keeps the Omarchy theme configured, and seeds `/var/lib/sddm/state.conf`:

```text
[Last]
User=$OMARCHY_USER
Session=omarchy.desktop
```

This state file matters because the current Omarchy SDDM theme uses `userModel.lastUser`; without a remembered user, SDDM can submit an empty username and show `Login failed` even when PAM/ZFS are otherwise correct.

## ZFS Packages

Stable ArchZFS OpenZFS packages are included during ISO creation:

```text
builder/build-iso.sh
builder/archinstall.packages
```

The build creates and includes:

```text
zfs-utils
zfs-dkms
```

Do not switch the ISO to an LTS kernel only to satisfy ArchZFS package compatibility unless the user explicitly asks for that tradeoff. The current approach keeps the normal Omarchy kernel choice and uses the stable `zfs-dkms` package when it supports the tracked kernel.

The online pacman configs include the ArchZFS experimental repo so the installed system can keep ZFS packages resolvable after installation:

```text
configs/pacman-online-stable.conf
configs/pacman-online-rc.conf
configs/pacman-online-edge.conf
```

The installer appends `[archzfs]` to the target pacman config only after the Omarchy install is complete, so the Omarchy install itself continues to use the ISO offline mirror.

## Rebuild Workflow

Run syntax checks before rebuilding if installer or harness files changed:

```bash
bash -n configs/airootfs/root/.automated_script.sh
bash -n configs/airootfs/root/configurator
bash -n builder/build-iso.sh
bash -n bin/omarchy-iso-make
bash -n bin/omarchy-iso-vm-test
git diff --check
```

Rebuild the ISO from local Omarchy source:

```bash
OMARCHY_PATH="$HOME/src/omarchy" ./bin/omarchy-iso-make --local-source --no-cache --no-boot-offer
```

If the build is running from an environment that cannot provide an interactive `sudo` password, enable passwordless sudo first:

```bash
omarchy-sudo-passwordless
```

Then run the normal build command. The build script always clears the host pacman package cache with `sudo rm -rf /var/cache/pacman/pkg/*` before starting Docker.

The rebuilt ISO is written under `release/`, typically:

```text
release/omarchy-YYYY.MM.DD-x86_64-master.iso
```

Generated ISOs, VM disks, screenshots, serial logs, and `release/vm-test/*` artifacts are test artifacts and should not be committed.

## Recent Workflow Findings

Do not use `OMARCHY_ISO_SKIP_PACMAN_CACHE_CLEAR`. That temporary escape hatch was removed from `bin/omarchy-iso-make` and `bin/omarchy-iso-vm-test`. The build always clears the host pacman package cache with `sudo rm -rf /var/cache/pacman/pkg/*` before Docker starts. If the agent cannot provide an interactive sudo password, ask the user to run:

```bash
omarchy-sudo-passwordless
```

Then run the normal build command without extra skip variables.

For manual visual testing, use `bin/omarchy-iso-boot`, not `bin/omarchy-iso-vm-test`. The VM test harness drives the installer automatically and is only for unattended validation.

If manual QEMU opens to a black screen, suspect OVMF booting the empty temporary disk instead of the ISO. The unsuccessful variation was relying only on `-boot once=d,order=c,menu=on,strict=on` while omitting per-device boot indexes. Keep explicit boot indexes in the manual boot helper:

```text
-device virtio-blk-pci,drive=drive0,bootindex=1
-device ide-cd,drive=cdrom0,bootindex=2
-boot once=d,menu=on
```

Fresh manual tests should recreate `/tmp/omarchy-iso-boot.qcow2` and `/tmp/OVMF_VARS.4m.fd`, boot the ISO once, then prefer the installed disk after reboot. Use `reuse` only when intentionally booting an existing temporary install.

ZFS must be treated as encrypted at the installer confirmation step. A previous bad variation mapped ZFS to `mode="unencrypted"`, which made the final destructive confirmation say `Yes, install without encryption` and wrote `user_encrypt_installation.txt` as `false`. ZFS installs always require encrypted per-user home datasets, so the configurator should skip the unencrypted question, show that ZFS homes are always encrypted, and write the install as encrypted.

## Automated Validation

Run the ZFS automated VM test after rebuilding:

```bash
OMARCHY_TEST_FILESYSTEM=zfs ./bin/omarchy-iso-vm-test --filesystem zfs --no-interactive-on-failure
```

If another manual QEMU instance is using SSH forward port `2222`, choose another port:

```bash
OMARCHY_TEST_FILESYSTEM=zfs OMARCHY_TEST_SSH_PORT=2223 ./bin/omarchy-iso-vm-test --filesystem zfs --no-interactive-on-failure
```

To test an already-built ISO without rebuilding:

```bash
OMARCHY_TEST_FILESYSTEM=zfs OMARCHY_TEST_SSH_PORT=2223 ./bin/omarchy-iso-vm-test --filesystem zfs --no-build --iso release/omarchy-YYYY.MM.DD-x86_64-master.iso --no-interactive-on-failure
```

The ZFS VM test drives the installer, waits for installation completion, boots the installed VM, and verifies:

```text
root filesystem is zfs
/home is zroot/data/home
/home/$USER is zroot/data/home/$USER
zpool zroot is healthy
zroot/ROOT/default, zroot/data/home, and zroot/data/home/$USER exist
user home encryption is enabled
user home keyformat is passphrase
user home keylocation is prompt
user home keystatus is available after login
pam_zfs_key.so is installed
/etc/pam.d/zfs-key exists
ZFS PAM auth unlock helper exists
system-login includes zfs-key auth/session hooks
system-auth does not include zfs-key auth/session hooks
system-auth includes zfs-key password-change hook
zfs-key auth/session hooks are login-service scoped
zfs-key mounts home during auth
zfs-key uses homes=zroot/data/home
hyprlock PAM keeps the packaged login include without a direct ZFS stack
SDDM autologin config does not exist
SDDM state remembers the installed user
SDDM state remembers omarchy.desktop
/boot/limine.conf contains root=ZFS=zroot/ROOT/default
/boot/limine.conf contains zfs_boot_only=1
mkinitcpio hooks include zfs filesystems
mkinitcpio hooks do not include zfs filesystems fsck
hostid is deadbeef
mkinitcpio includes /etc/hostid
UKI embeds etc/hostid
Omarchy source and Hypr config are visible under the real /home
/var/log/omarchy-install.log exists
[archzfs] is configured
zfs-dkms, zfs-utils, and limine-mkinitcpio-hook are installed
sddm is enabled
no swapfile or resume config exists
no failed systemd units exist
```

After a successful automated serial verification, run a direct graphical SDDM retry when the login path changed. Boot the installed VM with VNC or the normal visual helper, wait for SDDM, type the test password, press Enter, and capture before/after screenshots. A passing run should show the Omarchy desktop after login, not the SDDM `Login failed` message. The last known passing test used `release/vm-test/20260507-114422` and verified the desktop after password entry.

The verifier should fail if the installed ZFS boot emits:

```text
no pools available to import
```

Run a Btrfs regression test when the shared installer flow changed:

```bash
./bin/omarchy-iso-vm-test --filesystem btrfs --no-interactive-on-failure
```

## Manual Validation

For a clean manual visual install test, remove the temporary disk and OVMF variables first:

```bash
rm -f /tmp/omarchy-iso-boot.qcow2 /tmp/OVMF_VARS.4m.fd
./bin/omarchy-iso-boot release/omarchy-YYYY.MM.DD-x86_64-master.iso
```

Use `reuse` only when intentionally booting or continuing the previous temporary VM disk:

```bash
./bin/omarchy-iso-boot release/omarchy-YYYY.MM.DD-x86_64-master.iso reuse
```

The manual helper uses a normal QEMU GTK window with OpenGL disabled:

```text
-device virtio-vga,xres=1280,yres=800
-display gtk,gl=off,zoom-to-fit=on
```

Do not use VNC or the automated harness when the user specifically wants to manually interact with the installer.

## Common Failure Modes

If the installed ZFS system shows this during boot:

```text
ERROR: device 'ZFS=zroot/ROOT/default' not found. Skipping fsck.
```

Then a ZFS initramfs hook list still includes `fsck`. Fix the ZFS Omarchy hook generation so it uses `zfs filesystems` without `fsck`, then rebuild the ISO from the patched local Omarchy source.

If the installed ZFS system shows this during boot:

```text
no pools available to import
```

Check that the generated and final Limine cmdline contains `zfs_boot_only=1` and that `zfs-import-cache.service` is enabled in the target.

If Omarchy files appear missing after install but exist in hidden root dataset paths, suspect incorrect ZFS mount order. `zroot/ROOT/default` must be mounted at `/mnt` before child datasets like `zroot/data/home` and `zroot/var/log` are created.

If serial login works but graphical SDDM login fails with `Login failed`, check `/var/lib/sddm/state.conf`. The Omarchy theme relies on `userModel.lastUser`; without `User=$OMARCHY_USER`, SDDM may submit an empty username. Also verify `/etc/sddm.conf.d/autologin.conf` has been removed.

If login succeeds but `/home/$OMARCHY_USER` is not mounted from `zroot/data/home/$OMARCHY_USER`, check that `/usr/local/lib/omarchy/zfs-pam-unlock-home` exists and is executable, `/etc/pam.d/zfs-key` includes the `pam_exec.so expose_authtok seteuid` line, `pam_zfs_key.so` is present, `/etc/pam.d/zfs-key` auth/session hooks are included from `system-login`, and `keylocation=prompt` is set on the user home dataset. If the unmounted parent `/home/$OMARCHY_USER` contains stock Hyprland files, the user logged in without the encrypted home mounted and those files are decoys hiding the real encrypted home.

If the automated VM exits before live ISO login with a QEMU host forwarding error, another VM is probably using the default SSH port. Rerun with a different `OMARCHY_TEST_SSH_PORT`.

If GTK QEMU crashes with GL/DMABUF errors, keep `gtk,gl=off` and avoid `virtio-vga-gl` for manual ISO testing.
